# Evidence and claims

> 中文译本：如与英文原文 [evidence-and-claims.md](evidence-and-claims.md) 有出入，以原文为准。

状态：适用于 `3.21.0-mf` 的现行参考。当需要判断某个来源是否支撑某句陈述、或某项建议是否应保持条件式时，使用本文件。

## 保持各类对象相互独立

在工作笔记和报告中一律使用朴素的标签：

| 对象 | 含义 | 稳妥表述 |
|---|---|---|
| 来源断言 | 某个来源声称自己能做什么、发现了什么、测到了什么或承诺了什么 | “文档中称……” |
| 观察 | 智能体在明确说明的条件下实际读到、运行、看到或记录的内容 | “在此版本/本次运行中，我观察到……” |
| 研究主张 | 由一项或多项相关来源或观察支撑的陈述 | “现有证据支持……” |
| 推断 | 通过假设或解释把若干主张组合起来得出的结论 | “这表明……，因为……” |
| 决策或建议 | 针对特定场景与风险承受能力作出的选择 | “对于这种用途，我会……，前提是……” |

不要悄悄把表中某一行升格为另一行。一个来源可以在接口定义上具有权威性，但在性能问题上仍是薄弱证据。一次本地观察可能对某个配置而言很精确，却仍不足以支撑一般性的可靠性主张。

## 引用强度检验

对于与决策相关的主张，应检验主张与来源之间的关系，而不是给某个平台或作者贴上永久的质量标签：

1. **直接性**：该材料针对的正是这条主张，还是仅涉及相邻话题？
2. **可追溯性**：读者能否定位到相应段落、页码、数据行、代码修订、时间戳或运行时记录？
3. **方法与可信度**：输入、测量、方法、版本以及可能的利益关系是否足够透明，可供评估？
4. **范围匹配**：对象、版本、日期、司法辖区、环境、工作负载和任务是否与结论相符？
5. **质疑**：是否存在相关的独立佐证、反例、更正或竞争性解释？

判断出错所付出的代价以及推断的距离，决定了需要核验到什么程度。不要把来源数量折算成质量评分。同一来源的多个副本仍然只是同一个来源。

对于数值比较，要让数值始终带有相应的量、单位、条件和边界方向。单位相同并不意味着量可互换；来源测量值、推断目标值和用户限制各有不同的角色。最终建议中要保留原始约束；任何额外的估算都应标为推断，而不是悄悄升格为验收标准。

## 按主张类型选择证据

| 主张类型 | 有用的证据 | 须保留的边界 |
|---|---|---|
| 定义、接口、策略或版本行为 | 适用的官方文档、规范、发行说明，以及必要时查看源代码 | 已声明具备某项功能，并不证明其性能或本地运行成功 |
| 学术机理或实测效应 | 原始研究、方法/数据、更正历史、复现结果及合适的综述 | 基准测试结果不会自动迁移到另一种工作负载 |
| 当前实现行为 | 固定修订版、调用路径、测试、配置和运行时输出 | 仅有文件或 README 不能证明端到端行为 |
| 故障、维护或工程权衡 | 复现过程、issue/PR、维护者说明、透明的复盘（postmortem）、配置和结果 | 单起事件不能确立普遍性；单次成功不能确立可靠性 |
| 用户体验或操作实践 | 相关的访谈、转录、演示，或带有背景的社区报告 | 转录或演示可能省略条件，无法证明长期表现 |
| 采用度、需求或满意度 | 明确定义的指标、人群、分母、时间窗口和独立数据 | 星标数、搜索量、评论数和流行度不是可互换的指标 |

## 独立性与分歧

把重复同一份新闻稿、数据集、基准测试或原始帖子的来源归为一组。在出现独立方法或独立观察补充信息之前，视它们为同一谱系。当来源之间发生冲突时，先对齐定义、版本、样本、环境、测量方式和时间，再选择立场。如果冲突仍然与决策相关，应同时报告两种解释以及缺失的检验。

当用户的更正改变了对象、范围或预期决策时，应从当前论证中移除有依赖关系的主张，并把它们的历史保留为已被取代的状态。不要仅仅因为某个引用已经收集在手就继续保留它。

## 报告边界

让每句话的范围与实际检查过的部分和模态相符。转录只能支撑讲话的内容，不能确立屏幕上显示了什么。摘要或检索到的片段不能确立整篇论文中没有什么。代码片段不能确立完整系统实现了什么。同样的限制也适用于否定性主张：“现有片段不能确立 X”与“该来源中不包含 X”是两回事。

在放宽否定性陈述之前，先明确：要支撑它必须检查什么，以及这种检查是否会改变用户的决策。如果不会，就保留范围更窄的陈述。如果会，就在预算内检索相关的缺失部分；任何任务都不必默认检查所有模态或整个来源。

把证据附着在它所支撑的主张附近。并写明哪些内容未经检查：

- 页面或来源访问被阻止、被截断，或仅限于摘要；
- 证据属于来源断言，而非独立观察；
- 版本、日期或环境不一致；
- 某项建议依赖尚不清楚的用户偏好；
- 实验只是提出了方案，尚未运行。

与其使用“该工具是可靠的”这类无支撑的泛化陈述，不如使用“该版本在观察到的配置下完成了任务”这类有支撑的窄陈述。当条件和下一步核验都明确写出时，条件式建议就是有效的。

如需更深入的草案版证据模型，仅在任务专门涉及那段历史时，才参考本目录中带日期的归档文档。它们不是普通 Research Pro 工作所必需的台账或 schema。
