# Research quality checklist

> 中文译本：如与英文原文 [research-quality-checklist.md](research-quality-checklist.md) 有出入，以原文为准。

状态：适用于 `3.21.0-mf` 的现行检查辅助材料。它是一组问题，而不是来源数量、工具数量、轮次数量、评分或发布门槛。

## 意图与范围

- [ ] 结果是否回答了用户所述的用途和要求的形态？
- [ ] 对象、版本、日期、司法辖区、环境和约束是否清晰到足以支撑该结论？
- [ ] 研究是否始终处于用户的授权范围之内？
- [ ] 缺失的偏好、权限、实验或外部副作用是否已被指明？

## 证据

- [ ] 每条与决策相关的主张是否都有直接支撑它的来源或本地观察？
- [ ] 读者能否定位到相关段落、数据、代码修订、运行结果或时间戳？
- [ ] 证据角色是否清晰：来源断言、观察、主张、推断，还是建议？
- [ ] 重要的反例、更正、竞争性解释或来源冲突是否都已处理？
- [ ] 重复出现的来源是否被识别为同一谱系，而不是计作独立佐证？

## 访问与限制

- [ ] 被拒绝、被限流、被截断、仅有摘要、降级和未读取的来源是否都得到了准确标注？
- [ ] 措辞是否避免仅凭片段或摘要就宣称掌握了全文内容？
- [ ] 在版本、时效、工作负载和结论迁移限制影响决策之处，这些限制是否已明确写出？
- [ ] 当本地实际效果未知时，验证提案是否与已观察到的结果分开陈述？

## 预算与停止

- [ ] 重试、回退、并行工作、隐性用量和交付时间是否被当作同一份共享预算来对待？
- [ ] 每一步动作是否都有明确写出的理由，并且有改变答案的现实可能？
- [ ] 当证据已充分、预算耗尽或需要用户决策时，工作是否已停止？
- [ ] 如果结果不完整，是否说明了确切的缺口和最有价值的下一步核验？

## trace 与输出安全

- [ ] 脚本侧检索是否先用 doctor 检查，并通过相应的包装脚本/桥接运行？
- [ ] trace 可用时，外部调用是否都已记录，包括失败和降级路径？
- [ ] 交付物中是否不含机密信息、原始凭据、不安全的私有路径和不必要的原始响应？
- [ ] 最终的 trace 状态是否与实际覆盖情况和产物可用性一致？

某一项可以标注为“不适用”，并附上简短理由。走一遍清单并不会把条件性结论变成已验证的结论。
